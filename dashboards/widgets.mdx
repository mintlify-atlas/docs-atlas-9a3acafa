Widgets are the building blocks of every ThingsBoard dashboard. Each widget subscribes to one or more entity datasources, renders incoming data according to its type, and can expose actions such as sending RPC commands or navigating between dashboard states. The platform ships with over 100 built-in widget types organized into bundles, and every widget can be extended or replaced by a custom implementation written in HTML, CSS, and JavaScript.

---

## Widget Categories

ThingsBoard defines five first-class widget types in the `widgetType` enum (`widget.models.ts`). Each category has its own data subscription model and configuration dialog:

| Category | `widgetType` value | Examples |
|---|---|---|
| **Time-series** | `timeseries` | Line chart, Bar chart, Flot chart, Dygraph, State chart |
| **Latest values** | `latest` | Value card, Radial gauge, Linear gauge, LED indicator, Thermometer, Liquid level |
| **Control** | `rpc` | Round switch, Slider, Knob, Command button, GPIO control |
| **Alarms** | `alarm` | Alarms table, Alarm count badge |
| **Static** | `static` | HTML card, Image map, Markdown card, Label widget |

<Accordion title="Time-series widgets">
  Time-series widgets subscribe to historical and real-time telemetry streams. They render a series of `(timestamp, value)` pairs over the configured time window and update automatically as new data arrives. Aggregation is applied server-side before data is delivered to the widget, reducing payload size for long time ranges.

  The template widget for new time-series widget types is `system.time_series_chart`.
</Accordion>

<Accordion title="Latest values widgets">
  Latest-values widgets (`widgetType.latest`) display the most recent value of one or more telemetry keys or attributes. They do not use a time window—instead, they subscribe to entity attribute and telemetry update events and re-render whenever a new value arrives.

  The default template is `system.cards.attributes_card`.
</Accordion>

<Accordion title="Control widgets">
  Control widgets (`widgetType.rpc`) send RPC commands to a **target device**. The target device is configured independently from the datasource and resolves through the same alias mechanism. The widget type parameters expose `targetDeviceOptional: boolean` so that control widgets can optionally operate without a bound device when used in simulation mode.

  The default template is `system.gpio_widgets.basic_gpio_control`.
</Accordion>

<Accordion title="Alarm widgets">
  Alarm widgets (`widgetType.alarm`) query the platform alarm subsystem rather than telemetry. The datasource is an **alarm source** backed by an entity alias, and the widget receives paginated alarm objects including status, severity, originator, and custom details fields.

  The default template is `system.alarm_widgets.alarms_table`.
</Accordion>

<Accordion title="Static widgets">
  Static widgets (`widgetType.static`) render fixed content—HTML, Markdown, or images—that does not subscribe to any datasource. They are useful for labeling dashboard sections, embedding documentation, or displaying images that change based on CSS only.

  The default template is `system.cards.html_card`.
</Accordion>

## Widget Datasource Configuration

Every non-static widget is backed by one or more `Datasource` objects. Each datasource specifies an entity alias (or a direct device reference), the set of telemetry or attribute keys to subscribe to, and optional aggregation parameters.

### Datasource Types

The `DatasourceType` enum defines the available binding modes:

```typescript
// From widget.models.ts
export enum DatasourceType {
  function    = 'function',    // Simulated data generated by a JS function
  device      = 'device',      // Direct device binding (by device ID)
  entity      = 'entity',      // Entity alias binding (resolved at runtime)
  entityCount = 'entityCount', // Returns count of entities matching an alias
  alarmCount  = 'alarmCount'   // Returns count of alarms matching a source
}
```

For production dashboards use `entity` with an alias, not `device`. A direct device binding cannot be reused across tenants or redirected without editing the widget.

### Entity Alias Binding

Each datasource references an alias by its ID. When the dashboard loads, the `IAliasController` resolves all aliases to concrete entity lists and establishes WebSocket subscriptions for the selected data keys:

```typescript
// IAliasController.resolveDatasources (widget-api.models.ts)
resolveDatasources(
  datasources: Array<Datasource>,
  singleEntity?: boolean,
  pageSize?: number
): Observable<Array<Datasource>>;
```

### Telemetry Key Selection

Within each datasource you choose which **data keys** to subscribe to. A `DataKey` carries:

```typescript
// From widget.models.ts
export interface DataKey extends KeyInfo {
  type: DataKeyType;   // 'timeseries' | 'attribute' | 'entityField' | 'count' | 'alarm' | 'function'
  pattern?: string;    // label pattern, e.g. '${entityName} – temperature'
  title?: string;      // display name shown in the widget legend
  settings?: any;      // per-key visual settings (color, units, etc.)
  hidden?: boolean;    // exclude from legend without removing the subscription
}
```

### Aggregation Types

Time-series datasources support server-side aggregation before data reaches the widget. The `AggregationType` enum mirrors what ThingsBoard computes in the query layer:

```typescript
// From time.models.ts
export enum AggregationType {
  MIN   = 'MIN',
  MAX   = 'MAX',
  AVG   = 'AVG',
  SUM   = 'SUM',
  COUNT = 'COUNT',
  NONE  = 'NONE'   // raw samples, no downsampling
}
```

`NONE` delivers every stored data point within the time window. All other types bucket samples into equal-width intervals determined by the time window length and the `limit` parameter.

### Time Window Override

By default each time-series widget inherits the **dashboard-level time window**. To pin a widget to a fixed range regardless of what the user selects on the toolbar, enable **Use widget time window** in the widget's **Advanced** settings and configure an independent `Timewindow` object:

```typescript
// From time.models.ts
export interface Timewindow {
  displayValue?: string;
  displayTimezone?: boolean;
  hideInterval?: boolean;
  allowedAggTypes?: Array<AggregationType>;
  // realtime / history / aggregation sub-objects
}
```

## Widget Settings

Each widget exposes a **Settings** tab alongside the Data tab. Common settings present across all widget types include:

<Tabs>
  <Tab title="Title & Display">
    - **Title** — displayed in the widget header. Supports `${entityName}` and `${entityLabel}` dynamic substitution (see `widgetTitleAutocompleteValues` in `widget.models.ts`).
    - **Show title** — toggles the header bar; disabling it maximizes chart space.
    - **Background color** — widget card background.
    - **Padding** — inner spacing around the widget content area.
  </Tab>
  <Tab title="Legend">
    Configurable through `LegendConfig`:

    ```typescript
    // From widget.models.ts
    export interface LegendConfig {
      position: LegendPosition;  // 'bottom' | 'top' | 'left' | 'right'
      showMin: boolean;
      showMax: boolean;
      showAvg: boolean;
      showTotal: boolean;
      showLatest: boolean;
    }
    ```

    Enable or disable statistical columns (min, max, avg) and choose the legend position relative to the chart area.
  </Tab>
  <Tab title="Colors & Thresholds">
    Individual data key colors are set per-key in the **Data** tab. Many widgets also support **threshold lines** that draw horizontal markers at configurable values, useful for alerting operators to normal operating ranges.
  </Tab>
  <Tab title="Units & Decimals">
    - **Units** — appended to displayed values (e.g. `°C`, `kWh`). Supports ThingsBoard's `TbUnit` system for automatic unit conversion.
    - **Decimals** — number of digits after the decimal point.
    - **Post-processing function** — optional JavaScript expression applied to each raw value before display.
  </Tab>
</Tabs>

## Custom Widgets

Any widget type can be replaced or extended by writing your own HTML/CSS/JavaScript implementation. ThingsBoard provides a rich **Widget API** through the `WidgetContext` and the injected `self.ctx` object available inside the controller script.

<Steps>
  <Step title="Open the Widget Editor">
    Navigate to **Widget Library** in the left sidebar. Select an existing bundle (or create a new one), then click **+ Add new widget type** and choose the base category that matches your use case.
  </Step>
  <Step title="Define the template">
    The widget editor has three panels: **HTML** (the template), **CSS** (scoped styles), and **JavaScript** (the controller). A minimal time-series widget controller looks like:

    ```javascript
    self.onInit = function() {
      // self.ctx.data contains the subscribed telemetry
      // self.ctx.settings contains the configured widget settings
      self.ctx.$scope.latestValue = null;
    };

    self.onDataUpdated = function() {
      const data = self.ctx.data;
      if (data && data.length > 0 && data[0].data.length > 0) {
        const latest = data[0].data[data[0].data.length - 1];
        self.ctx.$scope.latestValue = latest[1]; // [timestamp, value]
        self.ctx.detectChanges();
      }
    };

    self.onDestroy = function() {};
    ```
  </Step>
  <Step title="Declare widget type parameters">
    Set the `WidgetTypeDescriptor` metadata—`sizeX`, `sizeY`, `defaultConfig`—to control the default dimensions and initial datasource configuration when the widget is placed on a dashboard.
  </Step>
  <Step title="Test and save">
    Use the **Run** button to preview the widget with live or simulated data. When satisfied, click **Save** to persist the widget type into the bundle.
  </Step>
</Steps>

### Available Widget API Methods

The controller script has access to the full `WidgetContext` object as `self.ctx`. Key properties include:

| Property | Description |
|---|---|
| `self.ctx.data` | Array of `DatasourceData` objects, each holding `{datasource, dataKey, data: [timestamp, value][]}` |
| `self.ctx.datasources` | Resolved datasource list with entity metadata |
| `self.ctx.settings` | Deserialized widget settings object |
| `self.ctx.widgetConfig` | Widget dimensions, title, and display settings |
| `self.ctx.stateController` | `IStateController` for state navigation |
| `self.ctx.aliasController` | `IAliasController` for alias resolution |
| `self.ctx.actionsApi` | Trigger widget actions (navigate, RPC, custom) |
| `self.ctx.detectChanges()` | Force Angular change detection after async updates |

## Widget Bundles

Widget types are organized into **bundles** (`WidgetsBundle`). A bundle groups related widgets under a shared alias and can be marked as `scada: true` to appear in the SCADA symbol library.

### Importing a Bundle

Export a bundle from one ThingsBoard instance as a JSON file, then import it into another:

1. Navigate to **Widget Library**.
2. Click the three-dot menu on the target bundle and choose **Export widget bundle**.
3. On the destination instance, click **Import widget bundle** and upload the JSON file.

The import endpoint is:

```
POST /api/widgetsBundle/import
Content-Type: application/json
Body: <exported bundle JSON>
```

### Exporting a Single Widget Type

```
GET /api/widgetType/{widgetTypeId}/export
```

The response is a self-contained JSON that includes the full `WidgetTypeDetails` descriptor, HTML template, CSS, and controller script. It can be re-imported on any instance via **Widget Library → Import widget type**.

<Note>
  For advanced analytics—cohort analysis, anomaly detection, predictive forecasting—ThingsBoard offers the **Trendz Analytics** add-on. Trendz integrates as a widget bundle and provides a point-and-click analytics designer whose output can be embedded directly in any dashboard as a native widget. It operates on the same entity model and alias system as built-in widgets, requiring no additional data pipelines.
</Note>
